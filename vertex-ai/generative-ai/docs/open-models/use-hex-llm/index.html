Serve open models using Hex-LLM premium container on Cloud TPU¶

Hex-LLM is a high-efficiency large language model (LLM) serving framework from Vertex AI, designed and optimized for Cloud TPU hardware. It combines state-of-the-art LLM serving technologies like continuous batching and PagedAttention with Google's custom optimizations for XLA and Cloud TPU. This makes Hex-LLM a powerful and cost-effective solution for serving open-source models on Google Cloud.

You can access Hex-LLM in Model Garden through the model playground, one-click deployment, and Colab Enterprise notebooks.

Before you begin¶

Concepts
  • XLA (Accelerated Linear Algebra): A domain-specific compiler for linear algebra that can accelerate TensorFlow models with minimal code changes.
  • PagedAttention: An attention algorithm that manages memory by partitioning the Key-Value cache into blocks, similar to how virtual memory paging works in operating systems, allowing for more efficient memory usage.
  • Continuous Batching: A scheduling algorithm that batches incoming requests continuously, processing them as soon as they arrive instead of waiting for a full batch to form, which improves GPU/TPU utilization and throughput.
  • Tensor Parallelism: A model parallelism technique where individual model layers (tensors) are split across multiple devices to handle models too large to fit on a single accelerator.
  • LoRA (Low-Rank Adaptation): A parameter-efficient fine-tuning (PEFT) technique that freezes pre-trained model weights and injects trainable rank decomposition matrices into the layers of the Transformer architecture, significantly reducing the number of trainable parameters.
Request Cloud TPU quota

In Model Garden, your default quota is 32 Cloud TPU v5e chips in the us-west1 region. This quota applies to one-click deployments and Colab Enterprise notebook deployments. To request a higher quota value, see Request a quota adjustment.

How to deploy models with Hex-LLM¶

You can deploy models using Hex-LLM in three ways, depending on your need for speed, simplicity, or customization.

Method Best For Customization Level
Playground Quickly testing a model with various prompts without any setup. Low (pre-configured endpoint)
One-click deployment Creating a dedicated, shareable endpoint with minimal configuration. Medium (select machine type)
Colab Enterprise notebook Full control over deployment, including server arguments and hardware configuration. High (fully customizable via SDK)

The Model Garden playground provides a pre-deployed Vertex AI endpoint that you can use to test a model immediately.

  1. Enter a prompt and, optionally, include arguments for your request.
  2. Click SUBMIT to get the model response.

Try it out with Gemma

You can deploy a model to a new, dedicated Vertex AI endpoint directly from the model card.

  1. Navigate to the model card page and click DEPLOY.
  2. Select a model variation and choose a Cloud TPU v5e machine type for deployment.
  3. Click DEPLOY to begin the deployment process. You will be notified when the endpoint is ready.

For maximum flexibility, use a Colab Enterprise notebook to deploy a model with custom configurations using the Vertex AI SDK for Python.

  1. Navigate to the model card page and click OPEN NOTEBOOK.
  2. Select the Vertex Serving notebook, which will open in Colab Enterprise.
  3. Run the cells in the notebook to deploy the model using Hex-LLM and send prediction requests.

The core deployment code snippet is as follows:

hexllm_args = [
    f"--model=google/gemma-2-9b-it",
    f"--tensor_parallel_size=4",
    f"--hbm_utilization_factor=0.8",
    f"--max_running_seqs=512",
]
hexllm_envs = {
    "PJRT_DEVICE": "TPU",
    "MODEL_ID": "google/gemma-2-9b-it",
    "DEPLOY_SOURCE": "notebook",
}
model = aiplatform.Model.upload(
    display_name="gemma-2-9b-it",
    serving_container_image_uri=HEXLLM_DOCKER_URI,
    serving_container_command=[
        "python", "-m", "hex_llm.server.api_server"
    ],
    serving_container_args=hexllm_args,
    serving_container_ports=[7080],
    serving_container_predict_route="/generate",
    serving_container_health_route="/ping",
    serving_container_environment_variables=hexllm_envs,
    serving_container_shared_memory_size_mb=(16 * 1024),
    serving_container_deployment_timeout=7200,
)

endpoint = aiplatform.Endpoint.create(display_name="gemma-2-9b-it-endpoint")
model.deploy(
    endpoint=endpoint,
    machine_type="ct5lp-hightpu-4t",
    deploy_request_timeout=1800,
    service_account="<your-service-account>",
    min_replica_count=1,
    max_replica_count=1,
)

Features of Hex-LLM¶

Key optimizations¶

  • Token-based continuous batching: Ensures hardware is fully utilized by processing a large number of concurrent requests efficiently.
  • Optimized attention kernels: A complete rewrite of attention kernels optimized for XLA.
  • Flexible parallelism: Composable data and tensor parallelism strategies with optimized weight sharding to run LLMs efficiently across multiple Cloud TPU chips.

Supported models¶

Hex-LLM supports a wide range of dense and sparse LLMs, including:

  • Gemma 2B, 7B, 9B, and 27B
  • Llama-2 7B, 13B, and 70B
  • Llama-3 8B and 70B
  • Llama-3.1 8B and 70B
  • Llama-3.2 1B and 3B
  • Llama-3.3 70B
  • Llama-Guard-3 1B and 8B
  • Llama-4 Scout-17B-16E
  • Mistral 7B
  • Mixtral 8x7B and 8x22B
  • Phi-3 mini and medium
  • Phi-4, Phi-4 reasoning and reasoning plus
  • Qwen-2 0.5B, 1.5B, and 7B
  • Qwen-2.5 0.5B, 1.5B, 7B, 14B, and 32B

Note: Hex-LLM can serve 70B models in full precision or quantized (INT8, INT4) precision.

General features¶

  • Single container: The API server, inference engine, and supported models are packaged into a single Docker image for easy deployment.
  • Hugging Face compatibility: Load models directly from a local disk, the Hugging Face Hub, or a Cloud Storage bucket.
  • Quantization: Supports quantization using bitsandbytes and AWQ.
  • Dynamic LoRA loading: Load LoRA weights on the fly by passing them in the request arguments during serving.

Advanced Features¶

Hex-LLM supports several advanced features to optimize performance for specific use cases.

Troubleshooting

If you encounter issues with code snippets or setup, refer to the Troubleshooting Guide.

Serve large models that cannot fit on a single host TPU VM (which contains at most eight v5e cores) by distributing them across multiple hosts.

To enable this feature, set --num_hosts in the container arguments and --tpu_topology in the Vertex AI SDK model upload request. The following example deploys the Llama 3.1 70B model on a 4x4 v5e TPU topology.

hexllm_args = [
    "--host=0.0.0.0",
    "--port=7080",
    "--model=meta-llama/Meta-Llama-3.1-70B",
    "--data_parallel_size=1",
    "--tensor_parallel_size=16",
    "--num_hosts=4",
    "--hbm_utilization_factor=0.9",
]

model = aiplatform.Model.upload(
    display_name=model_name,
    serving_container_image_uri=HEXLLM_DOCKER_URI,
    serving_container_command=["python", "-m", "hex_llm.server.api_server"],
    serving_container_args=hexllm_args,
    serving_container_ports=[7080],
    serving_container_predict_route="/generate",
    serving_container_health_route="/ping",
    serving_container_environment_variables=env_vars,
    serving_container_shared_memory_size_mb=(16 * 1024),  # 16 GB
    serving_container_deployment_timeout=7200,
    location=TPU_DEPLOYMENT_REGION,
)

model.deploy(
    endpoint=endpoint,
    machine_type=machine_type,
    tpu_topology="4x4",
    deploy_request_timeout=1800,
    service_account=service_account,
    min_replica_count=min_replica_count,
    max_replica_count=max_replica_count,
)

In general, the only changes needed are: 1. Set --tensor_parallel_size to the total number of cores in the TPU topology. 2. Set --num_hosts to the number of hosts in the TPU topology. 3. Set --tpu_topology with the Vertex AI SDK model upload API.

This is an experimental feature. It can only be enabled on a single-host setup, and performance is still under tuning.

Disaggregated serving separates the prefill and decode phases into different workloads to balance Time to First Token (TTFT) and Time Per Output Token (TPOT). This is useful for use cases with strict latency requirements.

To enable this feature, set --disagg_topo in the container arguments. The format is "number_of_prefill_workers,number_of_decode_workers".

hexllm_args = [
    "--host=0.0.0.0",
    "--port=7080",
    "--model=meta-llama/Llama-3.1-8B",
    "--data_parallel_size=1",
    "--tensor_parallel_size=2",
    "--disagg_topo=3,1",
    "--hbm_utilization_factor=0.9",
]

model = aiplatform.Model.upload(
    display_name=model_name,
    serving_container_image_uri=HEXLLM_DOCKER_URI,
    serving_container_command=["python", "-m", "hex_llm.server.api_server"],
    serving_container_args=hexllm_args,
    # ... other parameters
)

model.deploy(
    endpoint=endpoint,
    machine_type=machine_type,
    # ... other parameters
)

Prefix caching reduces Time to First Token (TTFT) for prompts that share a common prefix (e.g., system instructions, conversation history). Instead of recomputing the prefix, Hex-LLM caches the processed tokens.

To enable this feature, set --enable_prefix_cache_hbm in the container arguments.

hexllm_args = [
    "--host=0.0.0.0",
    "--port=7080",
    "--model=meta-llama/Llama-3.1-8B",
    "--data_parallel_size=1",
    "--tensor_parallel_size=4",
    "--hbm_utilization_factor=0.9",
    "--enable_prefix_cache_hbm",
]

model = aiplatform.Model.upload(
    display_name=model_name,
    serving_container_image_uri=HEXLLM_DOCKER_URI,
    # ... other parameters
)

model.deploy(
    endpoint=endpoint,
    machine_type=machine_type,
    # ... other parameters
)
The cached_tokens field in the API response indicates how many prompt tokens were a cache hit. 
"usage": {
  "prompt_tokens": 643,
  "total_tokens": 743,
  "completion_tokens": 100,
  "prompt_tokens_details": {
    "cached_tokens": 512
  }
}

Chunked prefill improves throughput and balances TTFT and TPOT by splitting a long prefill request into smaller chunks, which are then mixed with decode steps in a single batch.

To enable this feature, set --enable_chunked_prefill in the container arguments.

hexllm_args = [
    "--host=0.0.0.0",
    "--port=7080",
    "--model=meta-llama/Llama-3.1-8B",
    "--data_parallel_size=1",
    "--tensor_parallel_size=4",
    "--hbm_utilization_factor=0.9",
    "--enable_chunked_prefill",
]

model = aiplatform.Model.upload(
    display_name=model_name,
    serving_container_image_uri=HEXLLM_DOCKER_URI,
    # ... other parameters
)

model.deploy(
    endpoint=endpoint,
    machine_type=machine_type,
    # ... other parameters
)

Quantization reduces the computational and memory costs of inference by using low-precision data types (like INT4 or INT8) for model weights. Hex-LLM supports INT8 weight-only quantization and INT4 AWQ zero-point quantization for Mistral, Mixtral, and Llama model families.

No additional flag is required for serving quantized models; Hex-LLM automatically detects the quantized weights.

Server Configuration Reference¶

You can customize the Hex-LLM server by setting container arguments and environment variables. While one-click deployment uses pre-defined arguments, you can modify them in a notebook deployment for fine-grained control.

Server arguments and environment variables

Model

  • --model: The model to load. Can be a Hugging Face ID, a Cloud Storage path (gs://...), or a local path.
  • --tokenizer: The tokenizer to load. Defaults to the --model value if not set.
  • --tokenizer_mode: Tokenizer mode (auto or slow). Default is auto.
  • --trust_remote_code: Allow remote code from Hugging Face repos. Default is False.
  • --load_format: Checkpoint format (auto or dummy). Default is auto.
  • --max_model_len: Maximum context length (input + output). Defaults to the model's config.json.
  • --sliding_window: Overrides the model's sliding window attention size. For experimental use.
  • --seed: Seed for random number generators. Default is 0.

Inference engine

  • --num_hosts: The number of hosts to run on. Default is 1.
  • --disagg_topo: Defines prefill and decode workers for disaggregated serving (e.g., "3,1"). Default is None.
  • --data_parallel_size: Number of data parallel replicas. Default is 1.
  • --tensor_parallel_size: Number of tensor parallel replicas. Default is 1.
  • --worker_distributed_method: Distributed method (mp or ray). Default is mp.
  • --enable_jit: Enables Just-in-Time (JIT) compilation. Default is True.
  • --warmup: Warms up the server with sample requests. Default is True.
  • --max_prefill_seqs: Max sequences for prefilling per iteration. Default is 1.
  • --prefill_seqs_padding: Pads the prefill batch size to a multiple of this value. Default is 8.
  • --prefill_len_padding: Pads sequence length to a multiple of this value. Default is 512.
  • --max_decode_seqs/--max_running_seqs: Max sequences for decoding per iteration. Default is 256.
  • --decode_seqs_padding: Pads the decode batch size to a multiple of this value. Default is 8.
  • --decode_blocks_padding: Pads KV cache blocks to a multiple of this value. Default is 128.
  • --enable_prefix_cache_hbm: Enables prefix caching in HBM. Default is False.
  • --enable_chunked_prefill: Enables chunked prefill. Default is False.

Memory management

  • --hbm_utilization_factor: Percentage of free TPU HBM for KV cache. Default is 0.9.
  • --num_blocks: Fixed number of device blocks for KV cache. Overrides --hbm_utilization_factor.
  • --block_size: Tokens per block (8, 16, 32, 2048, 8192). Default is 32.

Dynamic LoRA

  • --enable_lora: Enables dynamic LoRA adapter loading. Default is False.
  • --max_lora_rank: Maximum supported LoRA rank. Default is 16.
  • --enable_lora_cache: Caches dynamic LoRA adapters. Default is True.
  • --max_num_mem_cached_lora: Max number of LoRA adapters in TPU memory cache. Default is 16.

Environment Variables

  • HEX_LLM_LOG_LEVEL: Logging level (e.g., INFO, DEBUG). Default is INFO.
  • HEX_LLM_VERBOSE_LOG: Enable detailed logging (true or false). Default is false.

Tune server arguments¶

Server arguments are interrelated and collectively impact performance. Follow this workflow to configure the Hex-LLM server for your use case.

  1. Select model: Determine the model family and variant (e.g., Llama 3.1 8B Instruct).
  2. Estimate memory: Calculate the minimum TPU memory needed: model_size * (bytes_per_parameter). For an 8B model with bfloat16 (2 bytes), you need at least 8 * 2 = 16 GB.
  3. Select hardware: Choose the smallest TPU configuration that meets your memory needs. For a 16 GB requirement, a ct5lp-hightpu-4t (4 chips, 64 GB total) is a good choice. You can then set --tensor_parallel_size=4.
  4. Set context length: Determine the maximum context length (input + output) for your use case (e.g., 4096) and set --max_model_len=4096.
  5. Tune KV cache: Tune the --hbm_utilization_factor to maximize KV cache allocation without causing out-of-memory errors. Start high (e.g., 0.95) and reduce if necessary.

Example: Llama 3.1 8B Instruct

python -m hex_llm.server.api_server \
    --model=meta-llama/Llama-3.1-8B-Instruct \
    --tensor_parallel_size=4 \
    --max_model_len=4096
    --hbm_utilization_factor=0.95

Example: Llama 3.1 70B Instruct AWQ on ct5lp-hightpu-4t

python -m hex_llm.server.api_server \
    --model=hugging-quants/Meta-Llama-3.1-70B-Instruct-AWQ-INT4 \
    --tensor_parallel_size=4 \
    --max_model_len=4096
    --hbm_utilization_factor=0.45
